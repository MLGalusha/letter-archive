# Layout benchmark results — 2026-07-28

## Decision

Upgrade the production layout runtime from Kraken 6.0.3 to Kraken 7.0.3, but
keep the current bundled BLLA model for the first migration.

That is an infrastructure and data-contract upgrade, not a claim that the
unchanged model detects handwriting better. The benchmark used the same
`blla.mlmodel` SHA-256 in Kraken 6 and Kraken 7 and produced the same number of
lines and regions. Kraken 7 is still the right base because its task API,
provider-neutral containers, plugin system, reading-order support, XML
interchange, forced alignment, and training workflow give the archive a clean
path to better models and human-corrected training data.

Do not replace Kraken's line detector with the tested Orli base model or
Eynollah line output. Eynollah's physical-page boundary is promising as an
optional preprocessing mask before Kraken, especially for photographs that
show a neighboring page.

## Migration status

The `kraken7-native-layout` branch now implements the safe first migration:

- Kraken 7.0.3 runs through `SegmentationTaskModel` and emits one strict native
  contract; the lossy rectangle-only interface has been removed.
- a single persistent Python process loads the model once per operator run;
- every effective Kraken option (including provider defaults and reading-order
  functions), every constrained inference package, the adapter and constraints
  checksums, platform, observed model device/dtype, precision, and process mode
  travels with every result;
- `PageLayoutV2` stores immutable source-bound engine evidence with native
  baselines or bboxes, polygons, regions, provider order, direction, model
  checksum, runtime, and stable IDs;
- mutable admin-review segments remain a separate projection. Existing review
  geometry and trust are preserved when canonical evidence is added;
- storage reads and writes validate schema, page identity, source checksum,
  canonical digest, and first-writer/source-revision fences;
- editor round trips retain native geometry and order. Human resize, move, and
  rotation transform associated baselines and word boxes without mutating the
  immutable detector document. Transcript rows missed by the detector remain
  editable but explicitly unlocated; the UI does not invent page boxes for
  them.

This first storage shape deliberately accepts one immutable canonical layout
per page. Before a fine-tuned model can become a production candidate, add a
versioned layout-run relation and an explicit “active review projection”
selection; a new model must never overwrite the prior canonical run merely
because it is newer.

No cloud worker was deployed as part of this migration. Detection remains an
operator-controlled local workflow until the same container is soak-tested and
approved for an on-demand, scale-to-zero job.

## What was tested

The fixed cohort contains every page from 14 complete letters: the six letters
selected by the archive owner plus one letter from every other collection.
There are 66 page images in total. The set includes EXIF-rotated scans, faint
and dense handwriting, ruled paper, mixed image/text pages, sideways
marginalia, and neighboring-page contamination.

Every accepted run records immutable source and prepared-image hashes, exact
engine configuration, model checksums, raw provider output, normalized layout,
overlay, timing, memory, and artifact integrity. The Admin Layout Lab presents
comparable pages as deterministic blind A/B trials.

Prepared-image identity uses two separate hashes. The encoded PNG SHA-256
protects the exact artifact bytes. A canonical decoded-raster fingerprint
protects the detector input pixels independently of the operating system's PNG
encoder:

`SHA-256("rgb8:<width>x<height>\n" + row-major RGB8 pixels)`

This distinction was necessary because 38 of 66 local-Kraken/cloud-Eynollah
PNG files had different encoded bytes even though all 66 pairs decoded to
identical RGB pixels. Existing immutable manifests remain unchanged; their
fingerprints are derived and integrity-checked lazily. Future manifests record
the fingerprint directly and freeze the fingerprint implementation in their
source provenance.

| Candidate | Scope | Result | Useful conclusion |
| --- | ---: | --- | --- |
| Kraken 6.0.3 + bundled BLLA | 66 pages | 66/66; 1,752 lines; 175 regions | Production baseline |
| Kraken 7.0.3 task API + same BLLA | 66 pages | 66/66; 1,752 lines; 175 regions | Safe engine/API migration; modestly faster in this cold-process benchmark |
| Kraken 7.0.3 + Orli base | Set 14 pages 1–2 plus ordinary-page control | Runaway/duplicated predictions on both Apple MPS and CPU | Not usable as a drop-in model for this archive |
| Eynollah model bundle 0.9.1 | 66 pages | 65/66; 663 provider polygons; 36 successful pages with zero lines | Reject its line output; retain page-boundary/region preprocessing as an experiment |

There is not yet complete human ground truth. Counts, pairwise agreement, and
reviewer preferences are evidence, but they are not absolute precision,
recall, or F1.

## Kraken 6 versus Kraken 7

The two full runs used the exact same bundled model:

`77a638a83c9e535620827a09e410ed36391e9e8e8126d5796a0f15b978186056`

Across the 1,752 normalized lines:

- all baselines were identical;
- all primary reading-order positions were identical;
- all line-to-region assignments were identical;
- six line boundaries and three region boundaries differed;
- both versions returned 1,752 lines and 175 regions.

The Kraken 7 run had a roughly 7% lower median total cold-page latency, a
roughly 9% lower median isolated-engine latency, and a roughly 14% lower median
provider-inference latency. Its peak resident memory was higher. These are
fresh-process-per-page measurements on one local machine, not persistent
worker throughput measurements.

A separate persistent-process soak loaded the Kraken 7 bundled BLLA model once
and then processed all 66 prepared pages sequentially on CPU with 32-bit
precision, batch size 1, and one inference thread. It completed in 663.575
seconds (10.05 seconds/page averaged across the complete run) and reached a
maximum resident set size of 1,850,490,880 bytes (1.72 GiB). The peak remained
bounded rather than growing once per page. This is the measurement used for
worker memory sizing; it is more representative than adding up package sizes
or extrapolating the cold-process peaks.

The isolated cold-process run ranged from 1.369 GiB to 2.024 GiB RSS, with a
1.671 GiB median and 1.925 GiB 90th percentile. Kraken does not publish a hard
RAM or VRAM minimum. For this archive, start CPU inference at 2–4 vCPU and
8 GiB RAM, concurrency 1. A 4 GiB worker is a possible measured minimum to test,
not the production default. GPU inference is unnecessary for the current
segmentation-only workflow.

For future segmentation fine-tuning, use a CUDA machine with 24 GiB VRAM
preferred (16 GiB as the practical trial floor), 8 vCPU, and 32 GiB host RAM.
That is a conservative engineering recommendation rather than an official
Kraken 7 requirement. Training should be a short-lived job; do not pay for an
idle GPU worker.

The result matters because it separates two decisions:

1. Kraken 7 is the better runtime and integration surface.
2. Better detection requires a better or fine-tuned model, different
   preprocessing, or both.

## What Kraken 7 changes for this archive

### Task API and complete layout objects

`SegmentationTaskModel` returns a consistent `Segmentation` object containing
baseline or bounding-box lines, polygons, regions, and reading-order data. The
current production script uses the legacy `blla.segment()` API and reduces each
line to a polygon and axis-aligned bounds. It discards the provider baseline,
region identity, provider reading order, tags, orientation evidence, model
provenance, and stable identity.

The new benchmark adapter already proves the task API can preserve those
fields. Production should adopt that contract instead of copying the older
lossy shape.

Baseline and bbox support is a typed union, not permission to treat the two as
equivalent. Kraken's conversion helpers are deliberately lossy: reducing a
baseline line to an axis-aligned box loses its native curve, while converting a
box to a baseline synthesizes a line rather than detecting one. Any legacy
projection must be labeled as derived and kept out of the canonical data.

### Reading order and rotated writing

Kraken supports horizontal and vertical principal text-direction hints, and
neural reading-order models are executed through the task API. A direction
hint does not automatically discover every rotated marginal note. For pages
like Set 14, likely candidates are a second rotated-region pass, a
domain-adapted layout model with a marginalia class, or a plugin model. The
resulting orientation and reading order must remain first-class data rather
than being replaced by a global top-to-bottom/left-to-right sort.

### Forced alignment

The task API can align a known transcription through a compatible recognition
model and return approximate character cuts. That can eventually connect a
verified transcript to image locations and produce word-level review targets.
It is not a substitute for correct line geometry, and it requires a suitable
recognition model and stable transcript-line identities first.

### Plugins and model experiments

Kraken 7 can load alternate segmentation, recognition, and reading-order
implementations through plugins without a second application-specific output
contract. Orli exercised this path but its published base model was unusable
on this archive. D-FINE is another official Kraken plugin candidate,
particularly for region segmentation; it should enter the same benchmark
rather than being wired directly into production.

### Training and measurable improvement

Experiment YAML files, explicit line/region class mappings, safetensors output,
and baseline detection precision/recall/F1 make a reproducible correction and
fine-tuning loop possible. Admin corrections can ultimately be exported as
PageXML or ALTO, split into fixed training/validation/test manifests, and used
to fine-tune a model that reflects these letters instead of generic archival
pages.

### Recognition throughput

Kraken 7's reported batching, parallel line extraction, and approximately 80%
CPU speedup apply to the recognition pipeline. They should not be described as
an automatic 80% layout-segmentation speedup. Recognition throughput needs a
separate warm-worker benchmark when the archive begins running local OCR/HTR.

### Kraken 7.0.3 details

The current release also makes recognition extract the line representation the
model was trained on unless explicitly overridden, supports distributed
recognition training, makes plugin loading more robust, fixes several CoreML,
dataset, and training issues, and updates bidirectional text handling to an
internal Unicode 17 implementation. These are valuable pipeline improvements,
but most do not change the bundled BLLA detector's predictions.

## Production integration problems found by the benchmark

The pre-migration detector and editor were built around a much smaller shape
than Kraken 7 can return. The `kraken7-native-layout` branch addresses these
items rather than preserving them as compatibility behavior:

- `python/line_finder.py` used the legacy API, discarded native baselines,
  regions, tags, IDs, and provider order, then globally sorted axis-aligned
  bounds by Y and X.
- `scripts/detect-lines-remote.ts` manufactured a horizontal baseline along
  the bottom of each bounding box.
- The backend persistence type required every line to have a baseline, so it
  could not honestly represent a native bbox-only or baseline-unavailable
  result.
- The line-segment request schema accepted `unknown[]`, and database/DTO reads
  cast unversioned JSON instead of validating a geometry contract.
- The frontend created temporary IDs on load, stripped them on save, globally
  re-sorted and renumbered the lines, and replaced every polygon-backed
  baseline with a horizontal box-center line.
- Detector output, human geometry changes, exclusions/classes, and transcript
  mappings were mixed in the same mutable object with no immutable engine
  result beneath the human overrides.

The audit also found an immediate workflow break independent of Kraken 7:
`detect-lines-remote.ts` requests
`/admin/processing/line-detection-queue`, but no such backend route exists in
the current source. Its upload sends only `lineSegments`, while the current
endpoint requires `primarySourceRevision` and `sourceChecksum`. This supported
local-detection path is repaired by the new source-fenced
`/admin/layout-processing/queue` and native PageLayout upload endpoints.

`python/kraken_segment.py` had no repository callers and contained a separate,
stale segmentation/recognition attempt. It calculated but did not use one
model path, accessed bbox data that baseline records do not provide, repeated
whole-page recognition, and suppressed recognition errors. It was removed;
`python/line_finder.py` now exposes only strict native output: a one-shot
`--native-json` path and a versioned sequential `--worker-native-json`
protocol. The remote CLI uses one worker/model load for its whole run.

## Other candidates

### Orli

The valid published-model configuration requires bfloat16. On Apple MPS, Set
14 page 1 hit the 768-line safety ceiling and page 2 emitted 105 heavily
duplicated/missed baselines. CPU bfloat16 repeated the failure: Set 14 page 1
hit a 128-line diagnostic ceiling, page 2 returned 109 poor lines, and the
ordinary control page `001-18881103-L01-01` also hit 128.

This rules out an Apple-MPS-only numerical problem and rules out the published
base model as a drop-in candidate. It does not rule out future fine-tuning once
the archive has trustworthy PageXML annotations.

### Eynollah

The CPU cloud run completed 65 of 66 pages in 65 minutes 52 seconds and reached
about 7.74 GiB maximum container memory. One page repeatedly failed inside
upstream skew selection.

Its line output is not suitable here:

- 36 of 65 successful pages had zero lines;
- on the six owner-selected letters, Kraken returned 653 lines across all 26
  pages while Eynollah returned 29 and returned none on 21 pages;
- many nonzero Eynollah polygons were word/blob fragments rather than complete
  handwritten lines.

After comparing canonical decoded rasters instead of PNG encoder bytes, all 65
successful Eynollah pages are valid comparisons with Kraken 7. The remaining
page is excluded only because Eynollah failed. Across those 65 pages, the
pairwise agreement proxy was:

- lines: 546 matches, 1,185 Kraken-only, 117 Eynollah-only; agreement F1
  `0.456`;
- regions: 93 matches, 80 Kraken-only, 320 Eynollah-only; agreement F1
  `0.317`;
- matched-region class agreement: `0.161`.

These are cross-provider agreement measures, not accuracy against human ground
truth. They reinforce the visual finding that the two line representations are
not interchangeable.

Its page boundary is genuinely useful. On Set 14 page 2 it excluded the visible
neighboring page that Kraken treats as part of the input frame. Broad region
predictions may also help, but some handwriting was classified as illustration
or `other`. The justified experiment is:

`Eynollah or D-FINE page/region mask -> Kraken 7 line segmentation`

It is not:

`Eynollah replaces Kraken line segmentation`

The temporary Google Compute Engine VM and disk were deleted after the
artifacts and attestation were copied back. No service account or inbound
firewall was attached, SpecFinder and existing Cloud Run resources were not
changed, and estimated compute cost was about $1.33.

## Pre-fine-tuning composition experiments

These experiments ask whether existing detectors can be composed more
intelligently before collecting training data. Every result is diagnostic,
non-rankable, local after the accepted Eynollah source run, and isolated from
the production database. No additional cloud machine was used.

### Rotating the page and combining Kraken results

A full unmasked 0/90/270-degree run kept every 0-degree BLLA line and admitted
only non-overlapping proposals from supported vertical zones. It completed all
66 pages and changed only four:

- `003-18880810-L01-01`: +29 displayed candidates;
- `003-18880810-L01-03`: +8;
- `014-18780127-L01-01`: +12;
- `014-18780127-L01-04`: +16.

The total increased from 1,752 to 1,817. Every page in the typed collection
009 and the contamination-control collection 010 was unchanged. This is the
first rotation policy that added plausible sideways handwriting without also
flooding ordinary horizontal pages.

An exact eight-page ablation then replayed five policies from the same frozen
0/90/180/270-degree provider evidence:

| Derived policy | Rotations admitted | Displayed candidates | Typed control `009-19470830-L01-03` |
| --- | --- | ---: | ---: |
| Raw union | 0/90/270 | 1,027 | 312 |
| Same-model consensus | 0/90/270 | 468 | 182 |
| Safe vertical zones | 0/90/270 | 322 | 47 |
| Same-model consensus | 0/90/180/270 | 551 | 182 |
| Safe vertical zones | 0/90/180/270 | 325 | 47 |

The raw union proves that “keep everything found in every rotation” is not a
usable rule. Same-model consensus is also insufficient: borders and typed
lines can be repeated consistently by the same model after rotation.

Adding the 180-degree pass to the safe policy produced only three additional
candidates across the eight pages: one on Set 14 page 4 and two on collection
003 page 1. The focused overlays make all three look plausibly like vertical
handwriting, but the fixed cohort contains no confirmed fully upside-down
page. A four-pass mode therefore remains useful as an optional diagnostic or
fallback, not yet the default: it adds about one-third more Kraken inference
than the three-pass policy for small observed recall.

### Eynollah page mask followed by rotated Kraken

The strict composition now has three explicit stages:

`Eynollah physical-page contour -> Kraken 7 at 0/90/270 -> safe vertical-zone selection`

Eynollah never supplies a displayed line. It only whites out pixels outside
its predicted physical-page contour; Kraken supplies all line geometry. A
paired eight-page run compared the exact contour (`p0`) with a 16-pixel
expansion (`p16`):

| Page | Strict contour p0 | Expanded contour p16 |
| --- | ---: | ---: |
| `014-18780127-L01-01` | 42 | 41 |
| `014-18780127-L01-02` | 32 | 32 |
| `014-18780127-L01-03` | 34 | 42 |
| `014-18780127-L01-04` | 38 | 39 |
| `003-18880810-L01-01` | 39 | 40 |
| `009-19470830-L01-03` | 46 | 46 |
| `001-18881103-L01-01` | 14 | 14 |
| `002-19001113-L01-01` | 28 | 27 |

Counts are not accuracy. The important visual difference is Set 14 page 3:
the strict contour removes more of the neighboring page, while the 16-pixel
padding reintroduces a visible sliver and eight additional detections. The
strict p0 composition is therefore the strongest current candidate for human
review. It is not production-ready: Eynollah failed one page in the complete
66-page source run, predicted boundaries can still be imperfect, reading order
for added rotated lines remains unresolved, and the evidence needs owner
judgment or page-boundary annotations.

The evidence-bearing reruns completed 8/8 pages for p0 and 8/9 for p16, with
the one p16 failure preserving Eynollah's known failed source page explicitly.
That is not evidence that p0 is more reliable: the p0 targeted cohort omitted
the known-failing collection 003 page 3, and p0 would fail closed on the same
unavailable Eynollah boundary.
Every successful derived page now contains byte-identical copies of
`page-mask.png`, `engine-input.png`, and `input-stage.v1.json`; its normalized
layout uses the source Eynollah contour rather than a frame fallback. Both runs
passed the authoritative TypeScript manifest, artifact-integrity, PNG
dimension, input-stage, and normalized-layout validator.

### D-FINE Nano region detector

The official LADaS D-FINE Nano checkpoint was also tested locally on seven
pages with Kraken 7.0.3 and `dfine_kraken` 0.4.2. It completed all seven,
peaked at 1.804 GiB RSS, and had 706.829 ms median D-FINE inference. At the
plugin's fixed 0.5 threshold it emitted only four small regions on three pages
and no broad text region. Kraken BLLA independently found 210 lines and the
task merger preserved all 210.

Nano is therefore rejected as a mask candidate on this evidence. This does not
reject D-FINE Large, which remains untested because its local memory
requirement exceeded the safe budget. The diagnostic preserved the exact
checkpoint hash, raw boxes, task merge, timings, peak memory samples, and
contact sheets.

### Current recommendation

Do not fine-tune yet. Put the strict Eynollah-mask plus three-rotation safe
Kraken composition in front of the archive owner in Layout Lab, compare it
against the unmasked BLLA baseline, and separately review the three candidates
added by 180 degrees. Use those judgments to decide:

1. whether Eynollah's boundary is reliable enough to justify a fallback policy
   for its failed or uncertain pages;
2. whether 180 degrees should run always or only for pages flagged as
   orientation-risky;
3. what page-boundary, line, orientation, and reading-order corrections must
   be captured as measurable ground truth.

Fine-tuning becomes justified only after those experiments leave a repeatable
error class that composition cannot solve and the archive has corrections to
train and score against.

## Production migration order

1. Introduce a versioned `PageLayoutV2` contract with source checksum/revision,
   stable line and region IDs, native baselines, native boundaries, region
   membership, orientation, reading order, classes, confidence, provider/model
   provenance, and explicit transcript links.
2. Restore one supported queue/upload path and enforce strict request/DTO
   validation. Store immutable detector output separately from human review
   overrides keyed by stable IDs.
3. Move the production worker to Kraken 7.0.3 in a fully locked Python 3.12
   environment using
   `SegmentationTaskModel` with the same BLLA model and CPU settings. Keep the
   current output available behind an adapter during the migration.
4. Stop the editor from globally re-sorting lines or replacing edited
   baselines with synthetic horizontal centerlines. Store geometry edits and
   reading-order edits independently.
5. Add an optional page-boundary/region preprocessing stage. Benchmark
   Eynollah and D-FINE masks against human page-boundary annotations before
   enabling either automatically.
6. Add a deliberate rotated-region experiment for sideways marginalia rather
   than changing the whole page's reading-direction hint.
7. After identities and geometry are stable, test a compatible handwriting
   recognizer plus forced alignment as an aid to transcript verification.
8. Export confirmed admin corrections to PageXML/ALTO, create fixed
   train/validation/test splits, and fine-tune/evaluate through versioned YAML
   experiments.

Do not automatically rewrite already reviewed production segments during the
runtime upgrade. Regeneration should be opt-in, source-checksum fenced, and
reviewed through the same benchmark/editor contract.

## Required tests for that migration

- strict `PageLayoutV2` rejection of malformed geometry, duplicate IDs,
  dangling order/region references, and unknown schema versions;
- task-API contract snapshots for baseline and bbox providers;
- parity on the fixed 66-page cohort before changing models;
- EXIF orientation (including malformed tags) and source-checksum fencing;
- round-trip PageXML/ALTO geometry and reading order;
- stable IDs across edits and reloads;
- detector reruns that cannot erase human review overrides;
- native-baseline preservation after polygon edits;
- explicit reading-order editing without coordinate re-sorting;
- Set 14 page-boundary exclusion and sideways-marginalia cases;
- failure, timeout, broken-pipe/OOM interruption, and partial-output
  publication;
- blind A/B review that cannot reveal provider identity before a verdict;
- fixed ground-truth test pages for baseline, region, orientation, order,
  split, merge, miss, and spurious-line metrics.

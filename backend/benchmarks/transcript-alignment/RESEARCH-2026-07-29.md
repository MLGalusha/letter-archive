# Transcript alignment research — 2026-07-29

## Finding

The shortest robust path is a content-aware monotonic join:

> authoritative LLM/human transcript ↔ noisy local HTR ↔ Kraken line geometry

The existing positional approach is fragile because one extra or missing
detected line can shift every later transcript line. Better page masks can
reduce bad proposals, but masks cannot establish which transcript text belongs
to which handwritten line.

## Evidence

### Ordered sequence alignment

- [Needleman and Wunsch](https://doi.org/10.1016/0022-2836(70)90057-4)
  established global dynamic-programming alignment with insertions and
  deletions.
- [Smith and Waterman](https://doi.org/10.1016/0022-2836(81)90087-5)
  established local sequence alignment. Local matching is useful for anchors,
  but a final local-only path could silently discard difficult transcript
  sections.
- [Wagner and Fischer](https://doi.org/10.1145/321796.321811) formalized
  character edit distance.
- [Gotoh](https://pubmed.ncbi.nlm.nih.gov/7166760/) introduced affine gaps,
  which let one neighboring-page block cost less than many unrelated gaps.
- [Gale and Church](https://aclanthology.org/J93-1004/) demonstrated ordered
  multi-unit alignment. That is the direct analogy for one transcript line
  matching two detected lines or two transcript lines matching one detection.

### Historical transcript-to-image alignment

- [Mapping Transcripts to Handwritten
  Text](https://www.cedar.buffalo.edu/~srihari/papers/IWFHR-2006-TranscriptMap.pdf)
  used rough recognition plus dynamic programming and explicitly addressed
  over- and under-segmentation.
- [Viterbi-based text/image
  alignment](https://aclanthology.org/W07-0902.pdf) combined recognition
  evidence and dynamic programming for known transcripts and measured both
  geometric mark error and alignment error rate.
- [OCR-Free Transcript
  Alignment](https://talhassner.github.io/home/publication/2013_ICDAR)
  demonstrated transcript alignment on degraded historical manuscripts.
- [AnyAlign](https://www.dfki.de/web/forschung/projekte-publikationen/publikation/10378)
  combined historical-document alignment with interactive correction.

These sources support the architecture. The exact score weights and confidence
thresholds in this repository are experiment hypotheses and must be calibrated
against human-labeled archive pages.

### Kraken 7

[Kraken’s task API](https://kraken.re/7.0/user_guide/api.html) separates:

- Segmentation: produces `BaselineLine` or `BBoxLine` geometry.
- Recognition: reads text from already detected lines.
- Forced alignment: places already assigned transcription into approximate
  character positions.

The forced-aligner example constructs a `BaselineLine` with its `text` already
filled. Therefore forced alignment cannot solve the initial page-transcript to
line assignment. It is valuable only after the content-aware join.

[Kraken 7’s changelog](https://kraken.re/main/changelog.html) documents the
new task API, recognition batching/parallel extraction, plugin architecture,
reading-order work, metrics, and vectorization fixes. Those are meaningful
infrastructure improvements, but a Kraken upgrade does not install a better
English handwriting recognition model or automatically add sideways-text
recovery.

### Local recognition model

[McCATMuS](https://zenodo.org/records/13788177) is the first local model:

- 16,173,802-byte Kraken `.mlmodel`.
- MD5 `e531463f631303c700750784b4f9ed63`.
- Local SHA-256
  `dfb911ba25fd11f93efc1b0c340957162981ecfdaac0ee1e26793d491f770244`.
- Handwritten, printed, and typewritten documents from the sixteenth through
  twenty-first centuries.
- Seven languages including English.
- More than 118,000 lines and almost four million characters.

The installed `en_best.mlmodel` is a printed-English model and is unsuitable
for judging cursive handwriting.

McCATMuS uses Kraken’s older polygon extractor but loads successfully in Kraken
7.0.3. The local adapter keeps the original curved baselines/polygons, closes
polygon rings as required by Kraken containers, and runs one CPU page at a time.

### Confidence and abstention

[Selective classification](https://proceedings.mlr.press/v130/gangrade21a.html)
formalizes the reject option: correctness among accepted predictions can be
optimized separately from coverage.

For this archive, a smaller set of nearly certain automatic mappings is safer
than a high-coverage result with invisible shifts. Mapping confidence must not
be copied from Kraken’s character confidence. It should consider:

- Best-versus-second-best complete alignment margin.
- Whether a line mapping persists across the best several paths.
- Text similarity.
- Strong anchors before and after it.
- Split/merge/gap type.
- HTR confidence.
- Geometry, region, and orientation plausibility.

Human corrections should become locked anchors, after which only the interval
between neighboring locked anchors is recomputed.

### Sideways and neighboring-page text

The proposed recovery path is:

1. Run the ordinary page flow.
2. Find unlocated transcript spans and suspicious image regions.
3. Recognize proposals in their native 0°, 90°, 180°, or 270° image.
4. Match their text fingerprints.
5. Project only accepted geometry back into source coordinates.
6. Deduplicate proposals and preserve separate flows for marginalia/sideways
   text when one page-wide reading order is not meaningful.

Eynollah may help identify the primary physical page or broad layout regions.
Kraken remains stronger for the individual baseline polygons used by the
editor. The combination is a proposal pipeline, not a reason to discard either
engine’s native evidence.

## OpenAI model-upgrade side experiment

This work is deliberately isolated from transcript-to-Kraken alignment.

The current application uses several model call sites with different tasks and
contracts. Luna, Terra, and Sol should be compared on the same frozen inputs,
prompt, schema, output limit, and reasoning setting. Only the model changes.

The first proposed sealed run is:

- Eight page images × three models = 24 transcription calls.
- Four frozen transcripts × three models = 12 entity-extraction calls.
- 36 calls total.
- Worst-case pre-call reservation estimate: approximately $4.32.
- Likely actual spend: approximately $2.

Transcription measures include CER, WER, physical-line-break F1, omission,
hallucination, severe proper-name/date/negation errors, and repair time.
Entity measures include schema success, entity/relationship precision and
recall, unsupported claims, and correction time.

Official OpenAI guidance supports representative evals and changing one
variable at a time:

- [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)
- [Image and vision inputs](https://developers.openai.com/api/docs/guides/images-vision)
- [Model selection](https://developers.openai.com/api/docs/guides/latest-model)
- [Pricing](https://developers.openai.com/api/docs/pricing)
- [Spend limits](https://developers.openai.com/api/docs/guides/spend-limits)

`detail: "original"` is the appropriate initial setting for OCR-sensitive
GPT-5.6 page comparisons. OpenAI also notes that spend-limit enforcement is not
instantaneous, which is why the repository uses an $18 local ceiling beneath
the user’s $20 authorization.

## Open questions to answer experimentally

- How much does many-to-many alignment improve over positional assignment?
- Which uncertainty features predict mapping correctness?
- Does rotated recovery add correct sideways mappings without false positives?
- Does an Eynollah page/region proposal improve Set 14 after content matching?
- Does forced character alignment materially improve the editor?
- Is local HTR still useful on AI-draft transcripts with transcription errors?
- Which GPT-5.6 model offers the best repair-time/cost tradeoff for page
  transcription and entity extraction?

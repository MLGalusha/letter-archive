# Reusable card previews — issue 122

Status: implementation candidate; independent review, comparable workload results,
CI, release and live acceptance remain pending. This is on-demand saving, not
pre-generation or a production backfill. Issue 50 remains open for overall image
readiness and physical iPhone acceptance.

## Behavior and boundary

The existing image route can save a completed 480px preview under
`STORAGE_DIR/image-previews-v1/<prefix>/<representation identity>.preview`. The
existing production mount maps STORAGE_DIR to the archive bucket at `/mnt/archive`.
There are no new SDKs, cloud resources, configuration settings, database records,
or public bucket URLs. Originals are never modified or deleted.

Only 480px AVIF, WebP and JPEG variants are eligible: at most three saved objects
per checked page/source/recipe version. Other widths, original downloads and
private/admin-only images retain their current behavior. Public images requested
with credentials may reuse the public representation, while their HTTP response
remains private and non-cacheable.

Representation identity is shared with the conditional-response change. It covers
page ID, source checksum/path/stat, width, format, encoding recipe and Sharp library
versions. The caller's `v` hint never controls the stored key. A source or encoding
change selects a different path rather than overwriting a previous version.

Access and source existence are checked before any reuse. Conditional 304 and
process-memory hits avoid durable storage. A durable hit avoids the transform
scheduler; publication, source identity and stat are checked again after its
asynchronous read. Newly generated bytes are checked before saving and again
after saving, so a publication/source change during storage cannot authorize
stale delivery. Hidden images do not read or populate the shared store.

## Complete-file validation and admission

Each object contains a 76-byte header (magic/schema, representation identity,
payload length, SHA-256) followed by raw encoded bytes. Readers validate the whole
envelope before returning any bytes. Missing, partial, corrupt, differently keyed,
or oversized objects are misses and fall back to the existing bounded transform.
Reads allocate at most the checked file size plus one byte and reject concurrent
growth, truncation and checksum disagreement. The payload limit is 2 MiB; larger
valid transforms can still be served but are not saved.

No correctness claim depends on exclusive creation, file locking or atomic rename.
Competing instances may duplicate a transform or encounter stale-file/write errors.
All storage errors fall back safely; interrupted files can be replaced by a later
successful request. The store never deletes a pathname that another writer might
be using. Same-mount simultaneous writes of a key are skipped by the local owner.

There are at most 40 concurrent reads and two writes per store instance, with no
waiting/background queue. Forty reads match the existing Cloud Run HTTP concurrency
and allow a normal 24-card warm burst to consult saved files. The maximum read
payload allocation is about 80 MiB plus headers, FUSE overhead and existing caches;
observed 480px response bodies in the earlier live sample were roughly 14–31 KiB.
This is a bound, not proof of an optimal Cloud Run memory/concurrency setting.

Accepted writes are awaited before the response completes. The first population
request pays upload time and one further access/source recheck. A full write budget
skips persistence and still serves the generated bytes; a future process miss can
therefore require encoding again. Writes do not hold the CPU transform scheduler's
slots, and no work is deliberately left running after sending the response.

Google documents the mount's non-POSIX concurrency, metadata cache and upload-memory
constraints. Cache visibility may lag between instances, so immediate reuse is not
guaranteed on every request. No mount options were changed.

## Lifecycle and observability

Saved bytes remain behind the image route. Unpublishing prevents public delivery;
it does not delete the private bucket object. Old source/recipe variants become
unreachable by current identity. There is no automatic garbage collection in this
change: total storage grows with historical source/recipe versions, even though
width/format cardinality and each object's size are bounded. Storage operations and
saved bytes have costs; no net cost or speed claim is made before measurement.

`Image response completed` adds `previewRead`, `previewReadMs`, `previewWrite`, and
`previewWriteMs` when applicable. Read outcomes distinguish hit/miss/invalid/error/
busy/unsupported; write outcomes distinguish saved/error/busy/unsupported/oversized.
`cache: saved` means durable reuse; existing hit/miss/not-modified meanings remain.
The normal queue/transform/access/version/whole-response timings remain available.
Read and write times include mount work; they do not isolate Cloud Storage network
or internal FUSE cache timings.

## Verification

The 65 focused tests and backend typecheck pass. Tests exercise fresh-process reuse, 24 simultaneous saved-file reads with
zero route transforms, complete/partial/corrupt/oversized files, simultaneous writers,
bounded admission and released capacity after failure. Route regressions cover
unsupported widths, private/admin images, failed storage fallbacks, publication or
DB/file source changes during both read and write, and conditional 304 bypassing
both storage operations as well as Sharp.

Controlled comparisons and release evidence will be appended when available.
Local filesystem tests establish application behavior; they do not emulate GCS
FUSE performance, cross-mount metadata caching, or physical iPhone rendering.

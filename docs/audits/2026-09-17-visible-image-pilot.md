# Local visible-image pilot

The controlled comparison confirms that saved 480px previews can survive a backend process restart and avoid another transform while returning identical bytes. It does **not** establish that production image waits are solved. The local scrolling workflow had no observed blank cards before or after the change, so it does not justify a frontend priority change. Issues #123 and #50 remain open for representative diagnosis and physical phone checks.

## Conditions

The [fixture owner](../../backend/scripts/serve-image-loading-fixture.mjs) creates a disposable PostgreSQL 16 database using registered migrations and 48 synthetic public letters. Collection 003 contains 35 cards and 009 contains 13. Three deterministic document-like JPEGs, copied to distinct page paths, provide geometry and compression variety: 1600×2200 (642,665 bytes), 2400×3200 (1,401,170 bytes), and 3200×2400 (1,394,078 bytes). This is not a representative sample of historical scans.

The built frontend and actual image, search, collection and content routes run through fixed loopback TLS origins: port 54433 for the frontend and 54434 for the API, with explicit local CORS. Chromium confirmed HTTP/2 for all captured image/search responses. The gateways stream to local HTTP/1 Express routes. Their scheduling, native loopback bandwidth and local filesystem are not Cloud Run or a phone network. External fonts are blocked by a local-only CSP, consistently using fallback fonts. Empty auxiliary public settings are a fixture response; image/search responses are never mocked.

Node 20.20.1, Sharp 0.35.4/libvips 8.18.6, eight logical CPUs, 390×664 CSS pixels and DPR 3 were used without CPU or network throttling. There were no production requests, shared database writes or changes to Cloud Run settings. All owned processes, containers and source files were cleaned up afterward.

## Workflow and comparisons

Each fresh browser opened Home, performed eight 350px scroll steps 700ms apart, then eight 700px steps 350ms apart, searched for `needle`, verified six results and settled for five seconds. The real `#app-scroll` container and normal pagination were used. Each phase requested 50 images: 48 distinct 480px representations, including one URL shared by the hero and its later archive card, plus the hero's 32px and 640px tiers. These are not 48 independently card-originated requests.

The first sequence compared #121 alone (`1a79974034ae8333e115e0e6c1e7c22e842d81b5`), #122 population (`934caf04c2d8dfc3845bcbe97fcffba11332aaaf`), and a fresh #122 process reusing saved variants. Only the route worker restarted; source paths, mtimes, database and frontend remained identical. A second dataset with identical generated bytes repeated the order as saved-warm then baseline, after one excluded population run. Every measured phase had a fresh process and browser context; saved-warm results cannot come from the previous process's memory cache.

All five measured phases returned the same 48 per-URL preview body hashes and 1,133,104 bytes at 480px. Each phase had 50 image responses with status 200, correct six-result search, and no recorded HTTP, request or page errors. Request IDs joined every 480px request to its backend log. Card-only timing excludes the seeded featured page `20000000-0000-0000-0000-000000000036` entirely, because its eager hero request can warm the later card. The remaining 47 requests had browser p50 / p95 of 135 / 433ms, 233 / 630ms, and 28 / 160ms in the first sequence; the reversed pair had 31 / 145ms saved-warm and 140 / 664ms baseline. Separate card-only route/cache statistics are retained in the evidence. This conservative exclusion does not attempt to infer which consumer initiated a shared request.

The first population sample was slower than baseline. Its preview reads were 1.19 / 9.63ms and writes 1.61 / 7.30ms at p50 / p95. Transform and queue timings also varied, so the entire difference cannot be attributed to persistence from this one sample. The reversed pair supports avoided transformation in the saved path, not a population-cost guarantee or a production speed ratio. Per-request percentiles within one workflow are not independent field samples.

All 48 cards were ready before their first observed visibility in every measured workflow: zero sampled blank-card time and zero unresolved cards, including cards later removed by search. That is a limitation for #123: this local test did not reproduce the production symptom. No image requests remained active when the search action began, so these runs do not test search under image contention. First-sequence action-start-to-results times were 352 / 481 / 292ms, including Playwright fill/autowait; native input-event-to-next-frame observations were separately 7.3 / 14.8 / 6.6ms. Neither is an INP measurement or a production latency claim.

## Measurement limits and reproducibility

The [browser script](../../e2e/scripts/visible-image-local.mjs) records request status, body hashes, browser priority events, visibility transitions, input events and server request IDs. Geometric visibility clips the scroll root and header but not arbitrary overlays. Readiness means complete, nonzero image dimensions and visible style, not measured paint. The 50ms sampler can assign the preceding interval to a newly visible card; delayed callbacks increase uncertainty. Already-ready first-visible waits are floored at zero. Summed card wait is not elapsed user wait. Search-driven removals are marked before the action and distinguished from unresolved mounted cards.

The [summary generator](../../e2e/scripts/summarize-visible-image-pilot.py) joins responses to logs by request ID, separates all `w=480` representations from non-hero cards, preserves failed/incomplete counts, uses `statistics.median`, and takes p95 at sorted index `ceil(n × .95) - 1`. Missing queue/transform samples indicate that phase was not logged, not a zero-duration transformation. The compact [evidence](evidence/2026-09-17-visible-image-pilot.json) retains per-request timing arrays, exact heads and content fingerprints. Full local request ledgers, logs and screenshots are under `output/visible-image-pilot/{pilot,reversed}/`; they are deliberately not committed.

To repeat:

1. Install the existing backend, frontend and e2e dependencies. Build the frontend with `VITE_API_URL=https://127.0.0.1:54434 npm run build`.
2. From backend run `node --import tsx scripts/serve-image-loading-fixture.mjs /absolute/new-output-directory`. It only creates its own database and fails if either fixed port is occupied; it never kills another listener.
3. The fixture starts the current checkout. Send `use /absolute/comparison-checkout` to select another backend with the same dependency lock, or `restart` for a fresh process retaining its saved files. Build/source hashes and worker PIDs are recorded. Select the #121 checkout explicitly when reproducing the baseline from a newer main branch.
4. From the repository root run `node e2e/scripts/visible-image-local.mjs /absolute/new-output-directory chromium unique-label`, then `python3 e2e/scripts/summarize-visible-image-pilot.py /absolute/new-output-directory`. Prefix excluded warmups with `excluded-`.
5. Stop the fixture owner with Ctrl-C to clean up its resources. Repeat WebKit only as a separately labelled compatibility confirmation, not as a comparison to warmed Chromium.

The initial smoke incorrectly used a relative API base unsupported by the real client and timed out before any API request. That failed artifact is preserved separately and excluded. The corrected smoke passed actual route/count/protocol/hash checks before timing began. Review subsequently clarified action timing labels, synchronous search-removal attribution, failed-request summarization and cleanup during startup. These fixes do not change the successful pilot's zero-unresolved or byte-parity results.

Automated review then identified the shared hero/card URL in the original width-only classification. Summaries now separate its representation from card-only timings without rerunning performance or changing raw evidence. New fixtures record the featured page ID explicitly. To summarize the retained earlier runs, pass their known seeded ID as the third argument: `20000000-0000-0000-0000-000000000036`; the generator refuses to guess if this context is absent.

Final verification passed both script syntax checks, the production frontend build, a startup SIGTERM cleanup check (owned container and temporary files removed), and a cancelled-request summary check (failure retained, excluded from completed timing samples). One separate WebKit 26.0 confirmation on merged main `bd23e037` observed 48 cards, 50 successful image requests, six correct search results and no recorded errors or sampled blank cards. This was compatibility confirmation, not a timed browser comparison or a physical iPhone test.

No frontend priority, image lookahead or application behavior changed. Revisit a visible-high/lookahead-low candidate only after a representative baseline demonstrates avoidable waiting; native priority may already suffice. Physical iPhone Safari/Chrome and production queue/network diagnosis remain separate acceptance work.
